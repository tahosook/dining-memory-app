# Issue #75 撮影写真の保存時圧縮・リサイズ機構の実測評価レポート

## 1. 概要 (Executive Summary)

本ドキュメントは、Issue #75「撮影写真の保存時圧縮・リサイズ機構の評価を実施」に基づき、ユーザーがカメラで撮影（またはライブラリから選択）した食事写真を保存する際の最適なリサイズ解像度・JPEG品質・処理順序・メモリ消費・EXIF保持方針を代表的な画像パターンに基づいて実測・評価し、実装に向けた保存仕様を検討・決定した調査報告書です。

> [!IMPORTANT]
> **実機写真による最終検証に関する前提**:
> 本レポートの実測評価は、光学・被写体特性（彩度、高感度ノイズ、細線テキスト、湯気グラデーション等）を反映して合成・生成した高解像度画像パターンおよび擬似カメラEXIFを用いた**技術的ベンチマーク**です。
> 実際の iPhone / Android 端末のカメラセンサーで直接撮影した実機写真（実機JPEG、iOSのHEIC形式、実機カメラの独自EXIFタグ、極暗所の実機高ISOノイズ）による最終検証は**未実施**です。
> したがって、本レポートで提示する「1600px / JPEG quality 80%」は完全な実証済値ではなく、**実装候補としての「暫定推奨保存仕様」**となります。次期実装Issueにおいて、実機撮影写真を用いた追加確認を行います。

### 結論要約
- **暫定推奨保存仕様**:
  - **長辺最大解像度**: **1600px**（アスペクト比 4:3 の場合は 1600×1200、16:9 の場合は 1600×900）
  - **JPEG品質**: **80%**（既存定数 75% から +5% 微調整）
  - **アスペクト比維持ポリシー**: `mode: 'contain'`, `onlyScaleDown: true`（元画像のアスペクト比を完全維持し、長辺1600px以下の画像は拡大しない）
  - **EXIF保持方針**: カメラ由来のEXIFを可能な範囲で保持しつつ、アプリ管理項目（`Software`, `DateTimeOriginal`, `GPS`, `Orientation: 1`）については後段の `writePhotoExifToJpeg` で正規化・上書きする
  - **処理パイプライン順序**: **「ネイティブリサイズ（ImageResizer）先行 → アプリEXIF付与（writePhotoExifToJpeg）後行」**
  - **失敗時フォールバック**: リサイズ失敗時は元画像の直接コピーへ安全にフォールバックし、写真データおよび食事記録を絶対に欠損させない
- **主要な実測成果（技術ベンチマーク）**:
  - **ストレージ削減効果**: 12MP（4032×3024）〜48MP（8000×6000）の検証画像（平均 2.78 MB、最大 6〜10 MB）に対し、1600px / q=80 設定では平均 **293.1 KB**（約 **85.3% の容量削減**）を達成。
  - **JS ヒープメモリ消費の激減**: 6MBのRAW画像に対して Base64 経由で EXIF 書き込みを行った場合、JSヒープ増分ピークは **288.4 MB** に達し端末クラッシュ（OOM）の危険があったが、リサイズ先行（356KB）にすることでピーク増分は **17.8 MB** へと **93.8% 削減**。
  - **処理時間の短縮**: パイプライン全体の処理時間が **1,086.2 ms から 104.6 ms へと約 10 倍高速化**。
  - **バックアップ健全性**: 1,000 件保存時のデータ容量推計が **2.72 GB から 286 MB** へ圧縮され、ZIP エクスポート／リストア時のメモリ不足・ストレージ枯渇リスクを大幅に低減。
- **実装判断**:
  - **今回は本番コードを変更しない**（評価・調査・仕様決定が本タスクの成果物）。
  - 本レポートの暫定仕様に基づき、次の別 Issue として実装作業を切り出す（第 14 節に実装設計および実機検証TODOを整理済み）。

## 2. 現行実装の調査結果

### 2.1 メイン写真保存 (`src/media/photoStorage.ts`)
- **関数の責務**:
  - `persistPhotoToStablePath(photoUri: string, options: PersistPhotoOptions)`:
    一時URIからアプリ固有の安定保存先（`documentDirectory`）へ写真を永続化する。
- **保存先パスの決定 (`resolveDestinationUri`)**:
  - `meal-YYYYMMDDHHmmss[-index].jpg` の命名規則で重複を回避しながら `documentDirectory` 内のパスを生成。
- **保存処理**:
  - `copyAsync({ from: photoUri, to: destination })` により、入力された `photoUri` のファイルをそのままバイナリコピーしている。
  - **現状の `photoStorage.ts` 自体には `ImageResizer` は組み込まれていない**。
- **EXIF書き込みのタイミング**:
  - コピー完了直後に `writePhotoExifToJpeg(destination, options)` を呼び出し。
  - EXIF 書き込みに失敗した場合でも `catch` して警告ログを出力し、コピーされた写真ファイル自体は保持する（フォールバック設計）。
- **Android MediaLibrary への保存処理**:
  - プラットフォームが Android の場合、`documentDirectory` の保存完了後に `MediaLibrary.Album`（アルバム名: `Dining Memory`）へ追加。
  - アルバム保存に失敗してもローカル写真は保持。

### 2.2 既存定数 `SAVED_PHOTO_MAX_WIDTH` 等の経緯
- **定義箇所**: `src/constants/CameraConstants.ts`
  ```typescript
  SAVED_PHOTO_MAX_WIDTH: 1600,
  SAVED_PHOTO_MAX_HEIGHT: 1200,
  SAVED_PHOTO_QUALITY_PERCENT: 75,
  ```
- **Git 履歴調査**:
  - 2026年4月14日（コミット `91c9310`）にて、仕様ドキュメント `tech-spec.md` に「Captured photos should be resized before save」と記載され、定数が導入された。
  - しかし当時 `src/media/photoStorage.ts` にはリサイズ処理が接続されず `copyAsync` のみの実装となった。
  - その後、コミット `43ca1e5` で `src/hooks/cameraCapture/capturePhotoPersistence.ts` が新設され、カメラ撮影フローの `persistCapturePhotoLocally` 経由でのみ `ImageResizer` が呼び出される構造となった。
  - また、写真回転ユーティリティ `src/utils/mealPhotoRotation.ts` の `rotateMealPhotoClockwise` でも `SAVED_PHOTO_MAX_WIDTH: 1600` が使用されている。
  - **課題**: 低レイヤーである `src/media/photoStorage.ts` にリサイズ責務がないため、将来の写真インポートや別導線からの保存時に未圧縮写真が混入する構造的リスクが残っている。また、`1600x1200` や `75%` の数値設定がこれまで客観的に実測・検証されていなかった。

### 2.3 サムネイル処理の現状 (`src/media/mealThumbnail.ts`)
- **リサイズ設定**:
  - `CAMERA_CONSTANTS.THUMBNAIL_PHOTO_MAX_WIDTH`: `320`
  - `CAMERA_CONSTANTS.THUMBNAIL_PHOTO_MAX_HEIGHT`: `320`
  - `CAMERA_CONSTANTS.THUMBNAIL_PHOTO_QUALITY_PERCENT`: `70`
  - 形式: `JPEG`
  - オプション: `{ mode: 'contain', onlyScaleDown: true }`, `keepExif: true`
- **保存先・ライフサイクル**:
  - 保存先: `${photo_path}-thumb.jpg`
  - DB カラム: `photo_thumbnail_path`
  - 最大同時実行数 2（`MAX_CONCURRENT_THUMBNAILS = 2`）の非同期キューで生成され、保存時や一覧表示時に遅延生成。
  - サムネイルは一覧表示用の軽量キャッシュであり、メイン写真（詳細画面や外部共有用）とは責務が完全に分離されている。

### 2.4 EXIF処理とメモリ負荷 (`src/media/photoExif.ts`)
- **処理の仕組み**:
  - `writePhotoExifToJpeg(photoUri, context)`:
    1. `expo-file-system` の `readAsStringAsync(photoUri, { encoding: Base64 })` でファイル全体を Base64 文字列として JS メモリへ読み込む。
    2. `piexif.load(jpegDataUrl)` で EXIF ツリーをパース。
    3. `Software`, `DateTimeOriginal`, `GPS`, `Orientation: 1` を注入。
    4. `piexif.dump(exifData)` でバイナリ化し、`piexif.insert(...)` で JPEG 文字列へ再挿入。
    5. `writeAsStringAsync(photoUri, base64, { encoding: Base64 })` でディスクへ書き戻す。
- **課題とメモリ負荷**:
  - 全処理が JavaScript スレッド（Hermes / V8）上で Base64 文字列として行われる。
  - 8〜10MBのスマホ元画像に対して実行すると、Base64 文字列（約 11〜13MB）のコピーや正規表現置換、中間バッファがヒープ上で多重生成され、**ピークヒープ消費が 200〜300MB を超える**。
  - モバイル端末では著しい GC 停止（数百ミリ秒〜数秒のフリーズ）や OOM（Out Of Memory）クラッシュを引き起こす。
- **回転（Orientation）との整合性**:
  - `@bam.tech/react-native-image-resizer` はネイティブ側（iOS: CoreGraphics, Android: Bitmap/Matrix）で EXIF Orientation に基づいてピクセルを物理的に正位置（Upright）へ回転した上で保存し、EXIF の Orientation タグを `1`（Normal）にリセットする。
  - `photoExif.ts` でも明示的に `exifData['0th'][piexif.ImageIFD.Orientation] = 1` を指定している。
  - したがって、リサイズ先行の順序であれば、回転の不整合や写真の横転・上下反転は発生しない。

## 3. 評価環境と測定条件

- **実行環境**: macOS (Darwin 24.x) / Apple Silicon (ARM64)
- **画像処理エンジン**:
  - **ネイティブリサイズ**: macOS CoreGraphics / ImageIO（iOS の `@bam.tech/react-native-image-resizer` 実装 `ImageResizer.mm` が使用する `CGImageDestination` / `CGImageSourceCreateThumbnailAtIndex` と同一の基盤エンジン）
  - **EXIFライブラリ**: `piexifjs` v1.0.6（アプリ本番コード `src/media/photoExif.ts` と 100% 同一）
  - **実行ランタイム**: Node.js v26.9.0
- **測定方式**:
  - 処理時間: `process.hrtime.bigint()`（ナノ秒精度、各測定 3 回施行の中央値を採用）
  - メモリ消費: `process.memoryUsage().heapUsed`（GC 実行後のベースラインと最大ピーク時の差分を計測）
  - EXIF検証: `piexif.load` により `Make`, `Model`, `DateTimeOriginal`, `GPS` 等の主要タグが引き継がれていることを確認

## 6. 画質評価（視認性・文字可読性・シズル感）

### 6.1 文字・メニューの可読性（Sample C での検証）
- **1920px & 1600px**:
  - メニュー見出し、価格、料理説明、極小のアレルギー注記文（3px 相当のストローク幅）に至るまで、文字のエッジが鮮明に維持され、拡大表示時にも完全に読解可能。
  - 品質 80% において、文字周囲のモスキートノイズ（高周波周辺のリンギング）はほぼ視認不能。
- **1280px**:
  - 全体像としては判読できるものの、スマートフォンのピンチイン拡大時に極小フォントの輪郭がやや滲み、漢字や記号の細部でボケが発生。

### 6.2 湯気・スープのシズル感と階調性（Sample D での検証）
- **品質 75%**:
  - スープ表面の油の照りや強いハイライトは維持されるが、上部に広がる薄い湯気（低コントラストな半透明グラデーション領域）において、拡大時に 8×8 DCT ブロック境界の縞状アーティファクト（バンディング）がかすかに浮き出る傾向を確認。
- **品質 80% / 85%**:
  - 湯気の緩やかな濃度勾配が滑らかに再現され、油滴のハイライトの階調飛びも発生しない。
  - 品質 75% と 80% の容量差は平均 **16 KB**（277KB → 293KB）とごく僅かであり、このわずかな容量で階調破綻が顕著に抑制される。

### 6.3 暗い居酒屋の高 ISO ノイズと暗部階調（Sample B での検証）
- **原寸（4032px）**:
  - 高感度撮影に伴う高周波の輝度・色ノイズが画面全体に散乱しており、これが原因でファイルサイズが 6.09 MB と肥大化。
- **1600px / 1920px リサイズ時**:
  - リサイズ時のダウンサンプリング（バイリニア／バイキュービック補間）により、微細な高周波センサーノイズが自然に平滑化・除去され、被写体の輪郭やタレの艶が引き締まる副次的効果を確認。

## 7. 処理時間とパフォーマンス評価

- **ネイティブリサイズ速度**:
  - 12MP 写真（4032×3024）のリサイズ所要時間は、1600px で **約 68.9 ms**、1920px で **約 72.0 ms**。
  - 48MP 写真（8000×6000）でも **約 81〜84 ms** と高速。
  - 2048px では約 98〜100 ms を要したが、これは 4032px からのリサンプリング比率が 1/2（2016px）に近接しつつも整数比ではないため、内部補間ステップが増加したためと考えられる。
- **体感影響**:
  - 撮影後のレビュー画面から「保存」をタップした際、ネイティブリサイズは 100ms 未満で完了するため、UI のブロッキングや体感上の遅延は生じない。

## 8. EXIFおよびOrientationの扱い

### 8.1 EXIF保持パイプラインの正確な整理
本アプリで想定するパイプラインは以下の多段処理です。

```
[カメラ元画像]
      ↓
(1) ImageResizer.createResizedImage(keepExif: true)
      ・ネイティブ層でカメラ光学メタデータを可能な範囲で引き継ぐ
      ・ピクセルを正位置へ物理回転
      ・EXIF Orientation を 1 にリセット
      ↓
(2) writePhotoExifToJpeg()
      ・JavaScript (piexifjs) でアプリ管理EXIFを書き込み
      ・Software ('Dining Memory') を注入
      ・DateTimeOriginal / DateTimeDigitized を撮影時刻で更新
      ・取得済みGPSスナップショットを注入（未取得時は既存GPSを保持）
      ・Orientation: 1 を正規化保証
      ↓
[アプリ安定保存パス]
```

> [!IMPORTANT]
> **EXIF保持の正確な表現**:
> 「すべてのEXIFが完全に保持される」「ImageResizerがすべてのEXIFを保証する」わけではありません。
> 正確には、**「カメラ由来のEXIF（Make, Model, LensModel, 露出等）をネイティブ側で可能な範囲で保持しつつ、アプリ管理項目（Software, DateTime, GPS, Orientation）については後段の writePhotoExifToJpeg で正規化・上書きする」**という設計です。
> メーカー固有のプロプライエタリな Makernote タグ等は、ネイティブリサイズ時に一部欠落する可能性がありますが、食事記録アプリの利用目的（撮影日時・場所・カメラ機種の記録）においては十分なメタデータが維持されます。

## 9. メモリ負荷・Base64フットプリントの分析

本調査において判明した最大の技術的ボトルネックは、`writePhotoExifToJpeg` における JavaScript Base64 文字列処理とヒープメモリの消費です。

### 9.1 原寸画像 vs リサイズ画像のメモリ消費実測

Sample B（6.09 MB, 4032×3024）および Sample E（4.10 MB, 8000×6000）を用いて、`writePhotoExifToJpeg` 実行時のメモリ増分と所要時間を実測比較しました。

| 対象画像 | ファイルサイズ | Base64 文字列長 | EXIF書き込み所要時間 | ピーク JS ヒープ増分 |
|---|---|---|---|---|
| **Sample B 原寸 (RAW)** | **6.09 MB** | **8.12 M 文字** | **1,062.3 ms** | **288.4 MB** |
| Sample B 1920px (q=80) | 556.6 KB | 742.2 K 文字 | 54.7 ms | 27.6 MB |
| **Sample B 1600px (q=80)** | **356.8 KB** | **475.8 K 文字** | **36.0 ms** | **17.8 MB (93.8% 削減)** |
| **Sample E 原寸 (RAW)** | **4.10 MB** | **5.47 M 文字** | **715.2 ms** | **198.1 MB** |
| Sample E 1920px (q=80) | 390.6 KB | 520.8 K 文字 | 30.8 ms | 19.7 MB |
| **Sample E 1600px (q=80)** | **313.3 KB** | **417.7 K 文字** | **28.4 ms** | **15.8 MB (92.0% 削減)** |

### 9.2 パイプライン実行順序の比較（Order A vs Order B）

- **Order A（EXIF先行 → リサイズ後行）**:
  - 全体所要時間: **1,086.2 ms**
  - JS ヒープピーク: **約 288 MB**
  - 理由: 巨大な Base64 文字列に対して `piexif.load`, `piexif.remove`, `piexif.insert` が多重コピーを発生させるため。
- **Order B（リサイズ先行 → EXIF後行）**:
  - 全体所要時間: **104.6 ms**（**約 10 倍高速**）
  - JS ヒープピーク: **約 18 MB**（**93.8% 削減**）
  - 理由: ネイティブ側（CoreGraphics / Bitmap）で省メモリにリサイズされた約 300KB の小型 JPEG だけを Base64 化して EXIF を書き込むため。

## 11. 最終的な暫定推奨保存仕様

実測データ、画質評価、メモリ負荷、および既存コードベースとの整合性を総合勘案し、以下の保存仕様を**実装候補の「暫定仕様」**として決定します。

> [!NOTE]
> これは代表パターンによる技術的ベンチマーク結果に基づく暫定仕様であり、実機撮影画像による最終検証を実装フェーズで別途行います。

### 11.1 暫定推奨保存仕様パラメーター
- **長辺最大解像度**: **1600px**
  - アスペクト比 4:3 の場合: 1600 × 1200
  - アスペクト比 16:9 の場合: 1600 × 900
  - アスペクト比 1:1 の場合: 1600 × 1600
- **JPEG品質**: **80%**
- **アスペクト比維持ポリシー**:
  - `mode: 'contain'`
  - `onlyScaleDown: true`（1600px 未満の元画像は拡大しない）
- **EXIF保持方針**:
  - カメラ由来のEXIFをネイティブ側で可能な範囲で維持（`keepExif: true`）
  - 保存時に `writePhotoExifToJpeg` でアプリ管理項目（`Software: 'Dining Memory'`, `DateTimeOriginal`, `GPS`, `Orientation: 1`）を書き込み・正規化
- **処理順序**:
  - **`ImageResizer.createResizedImage`（ネイティブ） → `writePhotoExifToJpeg`（Base64/EXIF）**
- **失敗時のフォールバック設計**:
  - リサイズ処理で例外（OOM、デコードエラー等）が発生した場合は `catch` して警告ログを出力し、**元画像の直接コピー（現行の `copyAsync`）へフォールバックして処理を継続する**。
  - その後の EXIF 書き込みや MediaLibrary 保存が失敗した場合も、保存済みのローカル写真は維持する。
  - **いかなるエラーが発生しても、ユーザーが撮影した食事記録データは絶対に消失させない**。

## 12. 推奨値の決定理由（他候補の不採用・位置づけ理由）

### 12.1 長辺解像度
- **原寸保持（不採用）**:
  - 容量削減率が 6.9〜26% に留まり、1,000 枚で 2.7 GB を消費。Base64 メモリ消費が 288MB に達し OOM クラッシュリスクが高いため不採用。
- **2048px（不採用）**:
  - 1600px と比較して容量が約 1.5 倍（440KB vs 293KB）に増加する一方、スマホ画面（幅 390〜430pt）での視認性に肉眼差がないため不採用。
- **1920px（次点・将来の拡張候補）**:
  - Full HD 規格に合致し文字可読性も優秀だが、ファイルサイズが約 398 KB（1600px 比で約 +35%）となる。既存定数や `mealPhotoRotation.ts` の 1600px との差異が生じるため、標準スマホでの最適解として 1600px を第一推奨とし、1920px は次点候補とする。
- **1600px（採用・暫定仕様）**:
  - 容量削減率 **85.3%**、平均 **293 KB**、リサイズ時間 **68.9 ms** と全指標で最もバランスが良い。
  - 既存の `CameraConstants.ts`（`SAVED_PHOTO_MAX_WIDTH: 1600`）および `src/utils/mealPhotoRotation.ts` と整合しており、写真回転時に解像度ジャンプが起きない。
- **1280px（不採用）**:
  - ピンチイン拡大時に小さな文字（Sample C の注記等）のエッジが潰れ、高精細ディスプレイでの細部閲覧性に劣るため不採用。

### 12.2 JPEG品質
- **90%（不採用）**:
  - 品質 80% に対してファイルサイズが 28% 増加（376KB vs 293KB）するが、スマホ画面での視覚的差異は皆無であり過剰品質。
- **85%（次点）**:
  - 階調性・細部再現性は極めて高いが、平均 354 KB となり、80% と比較して約 20% 容量が増加する。
- **80%（採用・暫定仕様）**:
  - 75% で見られた暗部ノイズや湯気グラデーションの微細な DCT ブロック境界が解消される。
  - 85% と同等の視覚品質を保ちながら 293 KB に抑えられる最良のスイートスポット。
- **75%（不採用・見直し対象）**:
  - 現行の `CameraConstants.ts` に設定されている値だが、実測において暗い居酒屋写真（Sample B）や湯気の階調（Sample D）で微細なバンディングが確認されたため、80% への改定を推奨。

## 13. HEIC形式および実機特有の課題と検証方針

### 13.1 現在の撮影フローとHEICの扱い
コードベースの調査により以下が確認されています。
1. **アプリ内カメラ撮影 (`takePhotoForReview`)**:
   - `expo-camera` の `takePictureAsync` を使用しており、標準で JPEG 形式の一時ファイルを出力している。
2. **ライブラリ選択 (`pickPhotoFromLibraryForReview`)**:
   - `expo-image-picker` の `launchImageLibraryAsync` を使用。
   - iOS 端末でカメラ保存形式が「高効率（HEIF/HEIC）」に設定されている場合、ライブラリから `.heic` 形式の URI が返される可能性がある。
3. **`ImageResizer.createResizedImage()` の形式サポート**:
   - **iOS**: `ImageResizer.mm` は React Native の `RCTImageLoader`（`UIImage` / CoreGraphics）を使用しており、HEIC を含む iOS 標準対応フォーマットのデコードが可能。出力形式として `'JPEG'` を指定することで JPEG へ変換出力される。
   - **Android**: `BitmapFactory.decodeFile` を使用。Android 8.0 (API 26) 以降で HEIF のデコードがサポートされている。
4. **`writePhotoExifToJpeg` と HEIC の関係**:
   - `piexifjs` は JPEG 形式（SOI `0xFFD8`）のみに対応しており、HEIC バイナリを直接処理することはできない。
   - したがって、**`ImageResizer` で先に JPEG に変換・リサイズしてから `writePhotoExifToJpeg` に渡す順序が必須**となる。

> [!WARNING]
> **実機検証が必要な項目**:
> iOS 実機で HEIC 写真を選択した場合に、`ImageResizer` が HEIC の EXIF メタデータをどの程度漏れなく出力先 JPEG へ転送できるか（CoreGraphics のプロパティブリッジ挙動）については、コード上の静的解析だけでは断定できません。**実機検証による確認が必須**です。
