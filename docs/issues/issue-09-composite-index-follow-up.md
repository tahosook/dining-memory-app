## 概要
本Issueは、**Issue #59 の調査・実測評価（`docs/notes/composite-index-evaluation-issue-59.md`）の結論（現時点は見送り）を引き継ぐ将来追跡用 Issue** です。
Records 一覧クエリに対する複合インデックス `idx_meals_is_deleted_datetime ON meals(is_deleted, meal_datetime DESC)` の導入について、現時点（データ規模 1,000 件以下）では体感改善効果が 0.1ms 未満であり不要なスキーマ更新を避けるため見送りと判断されました。本Issueは、将来データ件数が 10,000〜50,000 件規模に到達した際、またはクエリ要件変更時の再評価タスクとして追跡するためのものです。

## 関連 Issue および運用方針
- **先行 Issue**: #59（[perf(db): add composite index for records screen](https://github.com/tahosook/dining-memory-app/issues/59)）
- **推奨運用**:
  - Issue #59 は実測評価の完了および「現時点は見送り」という結論がドキュメント化されているため、#59 側は完了として Close することを推奨します。
  - 将来の再評価トリガー管理および再評価の実施は、本 Issue (#81) で一元的に追跡します。

## 現状の課題・背景
1. 現状構成では `USE TEMP B-TREE FOR ORDER BY` による全件ソートが発生するため、10,000 件で 0.68ms、50,000 件で 4.71ms とクエリ時間が増大する（複合インデックス導入時は 50,000 件でも 0.16ms で一定）。
2. ただし、不要な本番 DB マイグレーション（Version 2 → Version 3）を避けるため、現時点では導入が見送られている。
3. 加えて、StatsScreen や SearchScreen における `cuisine_type` 集計・検索頻度に対するインデックス最適化についても将来の検討余地がある。

## 再評価のトリガー条件（いずれかを満たした時点）
1. 保存レコード数が 10,000 件規模に到達したとき。
2. Records 一覧や検索画面の実機描画・実測性能でパフォーマンス課題が報告されたとき。
3. 一覧取得 SQL の要件や日付検索系の SQL が大幅に変更されたとき。

## 修正方針（トリガー到達時）
1. `docs/notes/composite-index-evaluation-issue-59.md` の DDL 構成イメージに基づき、Version 3 マイグレーションを作成する。
2. 既存の `idx_meals_is_deleted` の冗長性評価を行い、安全に削除可能かを全 SQL の影響調査とともに判断する。
3. 本番端末での起動時マイグレーション時間（ブロッキング時間）を検証した上で適用する。
